## 2. TTS, interruption and concurrency

Services/TextToSpeech/TextToSpeechService.cs:59-124 dispatches configured Windows, ElevenLabs, Kokoro, Piper or MiniMax speech with readiness/fallback policy. Existing clients, model managers and settings should be reused; cloud providers need explicit configuration and potentially paid credentials. Defaults must not silently select paid speech. The project already references NAudio.Wasapi2.3.0, org.k2fsa.sherpa.onnx1.13.0 and Larroy.Kokoro0.1.0 (OpenClaw.Tray.WinUI.csproj:118-120).

Current service paths obtain synthesized streams/complete audio byte arrays before PlayStreamAsync; they are not proof of incremental speech from an active agent token stream. PlayStreamAsync (464 onward) owns MediaPlayer, gate, cancellation and active-player lifetime; StopSpeaking (536) interrupts playback. Chat/OpenClawChatCoordinator.cs:105-166 routes configured/manual speech through the existing service. It mutes VoiceService capture during playback and restores it after300ms, preventing echo but also preventing straightforward audio barge-in detection. Some stop paths stop the active player, not necessarily ongoing synthesis/network requests. Investigate and test those lifetimes before promising immediate cancellation of all stages.

App.xaml.cs:3091 calls SpeakResponseAsync on chat notifications. This is an existing auto-read entry, not evidence that every streamed progress delta is automatically spoken. Task progress and final-response audio require a bounded, deduplicated policy: speak actual agent progress, never generate canned progress dialogue or block the tool runner while waiting for playback.

## 3. Core surfaces to reuse, not replace

- src/realtime-transcription/provider-types.ts:20-42 already defines onPartial/onTranscript/onSpeechStart/onError plus connect/sendAudio/close session contracts. src/gateway/talk/session-config.ts assembles realtime voice/transcription providers and agent-control capabilities. These are useful existing interfaces, **not proof the native Windows client supplies or consumes them today**. Evaluate transport/privacy/provider cost before choosing a remote transcription bridge over local recognition.
- src/talk/agent-consult-tool.ts and agent-run-control-shared.ts provide agent consultation and scoped status/cancel/steer/followup. The latter includes regex-based control-intent fallback. That fallback is not the desired general assistant architecture: Phase3 should use model-selected tools/control contracts, not extend voice-command phrase maps. Document existing compatibility behavior rather than silently removing it during voice work.
- src/tts/tts.ts and tts.runtime.ts support Core speech integration, but Windows' native playback is a separate owner. Avoid dual synthesis/playback of the same reply. Discord voice/voice-call extensions and macOS functionality are platform-specific examples, not Windows proof.
- src/agents/tools/sessions-spawn-tool.ts, subagents/spawn/subagent-spawn.ts and extensions/codex/src/app-server/native-subagent-monitor.ts already implement delegation/worker lifecycle. Retain one user-facing MORPHY and internal workers; reuse Codex for coding work instead of adding another coding-agent framework. Follow existing scope/consent/approval and cancellation ownership.

## 5. Recommended implementation order

1. **Endpointing consistency (small, first).** Route native ListenOnce silence configuration through the existing setting with validation/sensible bounds; retain intentional PTT behavior. Measure current2s baseline, then trial0.5–0.8s rather than asserting an optimal fixed value. Test pauses, soft speech, accents, noisy rooms, long dictation and timeout/stop flush. Keep configurable rollback. Do not add Silero integration until measurements show RMS is inadequate; then adapt the existing detector with a controlled comparison.
2. **Provisional transcription (medium–high).** Add an optional partial-output seam to the existing STT owner and bounded capture path, retaining final TranscribeAsync compatibility. First check pinned Whisper.net incremental callback capabilities; it currently returns only after full buffered transcription. If local rolling windows are necessary, bound their rate/audio horizon, use a generation/revision for replaceable partial text and reserve capacity for final recognition. Do not repeatedly submit partials to the agent or append unstable hypotheses as separate chat messages. Fall back visibly to final-only Whisper on unsupported devices/errors. A genuine streaming engine remains conditional, not a reason to import a second framework immediately.
3. **Speech lifecycle and interruption (medium–high).** Reuse TTS readiness/provider and MediaPlayer owners; first prove manual stop cancels synthesis/playback and drains safely. Then consider bounded sentence/chunk synthesis driven by real assistant output, ordered delivery, stale-generation dropping and deduplication between progress/final speech. Full automatic barge-in needs acoustic echo handling or a clearly limited half-duplex policy; muted capture cannot implement it. Keep stop-speech separate from cancel-model-run and cancel-tool; report effects that already occurred instead of promising rollback.
4. **Permission-aware screen observation (medium).** Integrate existing capture and CUA only after driver/policy verification. No background screen-watching default. Keep independent from speech engine changes.
5. **Optional pet (medium, later).** State observer only, disabled by default; no inference, capture or task ownership in the pet. Phase4 artwork/homepage remain separate.
6. **Delegation polish (medium).** Expose existing worker/run status behind MORPHY, using Codex-native workers where appropriate. This can be investigated independently of microphone/TTS. Do not make voice features depend on a new delegation implementation.

Optional wake-word investigation should proceed after push-to-talk/click activation and stop behavior are stable; do not gate the rest of Phase3 on it. Endpointing plus partial-transcript contracts share one capture/finalization test harness and can be delivered as coordinated small changes. Audio playback/barge-in is a separate change set with that same generation/session contract. Screen capture, pet and delegation remain independent releases to limit regressions.

## 7. Future homepage integration (Phase4 only)

The future central animated MORPHEUS logo should be a view/input adapter over the same WinUI chat/voice session owners. A click requests the existing permission-checked capture flow; provisional text renders as replaceable draft text; one finalized transcript goes through the real selected MORPHY session/model send path. Existing model/tool/delegation execution generates actual responses and progress. A bounded speech consumer reads those real events without awaiting playback in the execution path. Typed input stays available, and separate Settings stays intact.

Expose observable state derived from actual capture, run and playback events: idle/listening/thinking/speaking/executing plus visible screen-access activity. These states can overlap (speaking a progress update while a task executes), so model them as coordinated facts rather than an animation-owned mutually exclusive state machine. The homepage and optional pet project the same facts; neither becomes a new agent or controller. Tie updates to session/run/generation to prevent old speech/transcripts from changing a newly selected session.

Provide distinct controls for stopping playback, stopping capture and requesting run/action cancellation. Safe cancellation must use existing owner-held authority; already-completed actions are not undone. No hardcoded commands, response mappings, scripted conversations or canned jokes should drive this flow: the selected model reasons dynamically using context and allowed tools. Required sensitive-action confirmations remain visible. No homepage, logo animation, mockup, character artwork, new UI framework or additional application was created in Phase3A.

### Required Phase4 contract, supported by Phase3 foundations

1. Bind the existing homepage voice presentation and the main conversation view to the **same authoritative Gateway, MORPHY agent, canonical session key and provider thread**. MORPHY is the primary assistant; worker sessions stay internal. Do not assume thread IDs equal session keys or hardcode a legacy `agent:main:main` key. Use existing session resolution/materialization. If there is no conversation yet, let the normal first-send flow materialize one once and propagate its canonical identity to both presentations.
2. Keep partial recognition in replaceable, transient input state only. A final utterance is submitted once through shared composer/provider admission as an ordinary user message. It must not appear as an additional completed user message merely because the final recognizer event follows several partials. The current dictation-to-draft path can remain for typed chat; automatic final submission belongs to an explicitly activated voice interaction mode.
3. The normal Gateway/session history is the only persistent conversation. Main chat must show all finalized voice requests, actual assistant replies and existing tool activity without importing/copying homepage records. Voice input carries no separate persistent history. Reopening either view never creates a session as a side effect of visual navigation.
4. Capture the authoritative session identity and utterance operation when listening starts. If the session, agent, Gateway, user intent or surface generation changes, invalidate or explicitly settle that capture; never silently retarget a late final into another agent/session. View switching may retain the capture/run under its existing owner, but must not start a second one. Define that ownership before implementation.
5. Maintain one send-operation/idempotency identity through acknowledgement and any supported reconciliation. Calling the normal SendMessage API again creates a new operation: it is **not** a safe way to retry an uncertain prior send. After disconnect/timeout, use existing operation outcome/history/run reconciliation; do not mint a new key and resubmit merely because the homepage looks empty. Reject stale finals and duplicate handler events. If the current owner cannot reconcile an unknown result, expose uncertainty and require deliberate recovery instead of promising exactly-once execution. No new persistence store is proposed.
6. Observe actual assistant and task events for the same session/run to render current status and feed speech. Spoken output must derive from generated assistant text, with chunk/final deduplication and existing speech sanitization, not canned dialogue or a second model conversation. Do not narrate hidden reasoning or speak every internal tool payload. Progress announcements remain progress until authoritative terminal success/failure/cancellation arrives; finishing a playback item never completes a task.
7. Separate stop-capture, stop-playback and cancel-run/action controls. Cancellation and reconnect handling must retain existing approval and execution authorities and report irreversible effects/uncertain outcomes. Keeping the voice view minimal never hides required consent, an actionable error or a sensitive-action approval. Preserve typed interaction and the existing separate Settings window.

### Homepage presentation lifecycle: no history

The existing homepage will be a minimal voice command center centered on the animated MORPHEUS logo in Phase4. It may show only the current provisional transcript, current spoken response and active task status. It must not display a scrolling timeline, previous conversations or historical message rows. The main chat remains the complete conversation view.

After an interaction reaches an authoritative terminal state and relevant playback has settled, an accessible configurable/appropriate display delay may clear its **presentation fields only**. Do not choose an arbitrary global timeout before UX review. Bind any delayed clear to the interaction/session/run generation: an old timer must never clear a newer utterance, active task, error requiring attention or approval. A still-active background task can remain visible independently of the completed speech text.

Clearing the homepage must never call DeleteThreadAsync, clear history/memory, create a new session, reset an agent, cancel a run, discard queued work or overwrite the chat draft. It does not mutate persisted messages or the provider's authoritative conversation. Reentering Home is clean idle by default, with a projection of genuinely active work for the same conversation if any; do not repopulate old replies from history merely because the provider restored its snapshot. After reconnect, derive active work from current owner/runtime facts, not a stale last-message or animation state.

The projection may hold ephemeral text and timer state, but is not a second conversation, task lifecycle owner or message database. Existing events/history remain available to main chat while the homepage is visually empty. Switching presentations during a task must retain full context and the same session; no message duplication or post-execution copying is permitted.

### Technical gaps and acceptance cases

These invariants are proposed requirements, not already-working behavior. Current Home and chat are the same mounted surface; a new visual mode needs a narrow presentation contract that shares the existing provider/session lifetime. Current voice composer capture appends a draft rather than automatically sending; its shared send admission must be exposed/reused safely for the future mode. Current event callbacks exist but are not yet a clean-home transient projection or a deduplicated speech-progress feed. Cross-reconnect idempotency retention and unknown-outcome recovery need explicit tests at the current owner; random per-call keys alone are insufficient. Automatic partial recognition and full-duplex interruption are still the gaps documented above.

Add focused existing-owner tests for: one voice final→one normal user message; duplicate final callbacks; partials never persisted; lost acknowledgement/reconnect without second execution; stale completion after session change; identical main-chat history before/after visual clear; navigation without session creation; new-session materialization once; reopening Home without replaying old text; active task surviving navigation; delayed clear not hiding a newer interaction; terminal versus progress distinction; speech chunks not repeated on reconnect; independent playback/run cancellation; and visible approval/security errors from either presentation. Test same-run text, task/tool events and persisted history via the existing Gateway fixture, then prove the real Windows/model path. Assert persisted session/message identity directly, not screenshots alone.

Phase3 may establish the voice, send/finalization, lifecycle and observable-state seams needed for these tests. Phase4 alone will repurpose the existing homepage and implement animated-logo interaction. No second homepage, conversation history, persistent homepage storage, artwork, UI framework or application is proposed or implemented.
